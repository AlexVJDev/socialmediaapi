# Пользовательская лента

Лента — список опубликованных записей авторов, на которых подписан пользователь. Отдельной таблицы ленты нет: лента строится при чтении одним SQL-запросом из `subscriptions` и `posts` (`FeedRepository` / `FeedRepositoryJdbc`).

## Как строится

```
текущий пользователь
  → его подписки
  → опубликованные посты авторов
  → сортировка от новых к старым
  → страница результата
```

```sql
SELECT p.id, p.author_id, p.title, p.content,
       p.status, p.created_at, p.updated_at
FROM subscriptions s
JOIN posts p ON p.author_id = s.followed_id
WHERE s.follower_id = ?
  AND p.status = 'PUBLISHED'
ORDER BY p.created_at DESC, p.id DESC
LIMIT ? OFFSET ?
```

## Что входит в ленту

- Только публикации в статусе `PUBLISHED`: удалённые (`DELETED`) не показываются.
- Только публикации авторов, на которых пользователь подписан. После подписки посты автора появляются в ленте, после отписки — исчезают; сами публикации при этом не меняются.
- Собственные публикации пользователя в его ленту не входят: подписка на себя запрещена (`chk_subscriptions_different_users`).
- После принятия предложения дружбы оба друга видят публикации друг друга, потому что процесс создаёт взаимные подписки (см. `FriendshipRequest.md`).

## Порядок

От новых к старым: `created_at DESC, id DESC`. Идентификатор — второй ключ сортировки: несколько публикаций могут иметь одинаковое время, и без него их порядок не определён — одна и та же запись могла бы попасть на две соседние страницы или не попасть ни на одну.

Индексы: `idx_subscriptions_follower` находит подписки пользователя, `idx_posts_author_created (author_id, created_at DESC, id DESC)` отдаёт посты каждого автора уже в нужном порядке.

## Страницы: `limit` и `offset`

Первая реализация использует offset pagination: `limit` — размер страницы (больше нуля), `offset` — сколько записей пропустить (не меньше нуля). Некорректные значения отклоняются `IllegalArgumentException` до обращения к БД.

### Ограничения offset pagination

- **Глубокие страницы медленные.** `OFFSET N` не «перепрыгивает» записи: PostgreSQL собирает и сортирует первые `N + limit` строк и отбрасывает `N` из них. Чем дальше страница и больше лента, тем дороже запрос.
- **На быстро меняющейся ленте страницы «плывут».** Номер страницы считается от верха ленты в момент запроса:
  - новая публикация сверху сдвигает всё вниз — на следующей странице читатель снова видит последнюю запись предыдущей (дубль);
  - удаление публикации или отписка от автора сдвигает всё вверх — одна запись не попадает ни на одну страницу (пропуск).
- Поэтому offset подходит для первой версии и небольших лент, но не для бесконечной прокрутки большой и активной ленты.

### Развитие: cursor (keyset) pagination

Следующая страница запрашивается не по номеру, а от последней показанной записи — по паре `(created_at, id)`:

```sql
SELECT p.id, p.author_id, p.title, p.content,
       p.status, p.created_at, p.updated_at
FROM subscriptions s
JOIN posts p ON p.author_id = s.followed_id
WHERE s.follower_id = ?
  AND p.status = 'PUBLISHED'
  AND (p.created_at, p.id) < (?, ?)
ORDER BY p.created_at DESC, p.id DESC
LIMIT ?
```

Стоимость запроса не зависит от глубины страницы, а новые и удалённые записи не вызывают дублей и пропусков. Индекс `idx_posts_author_created` подходит и для этого варианта. Это отдельное развитие процесса, в текущей реализации его нет.
