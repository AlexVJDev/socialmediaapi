# Пользовательская лента

Лента — список опубликованных записей авторов, на которых подписан пользователь. Отдельной таблицы ленты нет: лента собирается при чтении (fan-out on read) одним SQL-запросом из `subscriptions` и `posts` (`FeedRepository` / `FeedPersistenceAdapter`, модуль `posts`). Почему так и какие варианты отвергнуты — разделы «Профиль нагрузки и выбор решения» и «Развитие»; подробный разбор с замерами — `docs/md/task/41215-2/README.md`.

## Что входит в ленту

- Только публикации в статусе `PUBLISHED`: удалённые (`DELETED`) не показываются.
- Только публикации авторов, на которых пользователь подписан. После подписки посты автора появляются в ленте, после отписки — исчезают; сами публикации при этом не меняются.
- Собственные публикации пользователя в его ленту не входят: подписка на себя запрещена (`chk_subscriptions_different_users`).
- После принятия предложения дружбы оба друга видят публикации друг друга, потому что процесс создаёт взаимные подписки (см. `FriendshipRequest.md`). После отклонения лента не меняется: отправитель остаётся подписан на получателя, обратной подписки нет. Сквозная проверка через HTTP — `FriendshipFeedTest` (корневой пакет тестов).

## Порядок

От новых к старым: `created_at DESC, id DESC`. Идентификатор — второй ключ сортировки: несколько публикаций могут иметь одинаковое время, и без него их порядок не определён — одна и та же запись могла бы попасть на две соседние страницы или не попасть ни на одну.

## Как строится

```
текущий пользователь
  → его подписки                                  (uq_subscriptions_users)
  → по каждому автору — не больше limit + 1
    самых свежих опубликованных постов            (idx_posts_published_author_created)
  → объединение, сортировка, первые limit + 1
  → колонки постов страницы по первичному ключу
```

```sql
WITH page AS (
    SELECT  lp.id
        FROM subscriptions s
            CROSS JOIN LATERAL (
                SELECT  p.id,
                        p.created_at
                    FROM posts p
                    WHERE p.author_id = s.followed_id
                        AND p.status = 'PUBLISHED'
                        AND (p.created_at, p.id) < (?, ?)   -- только для следующих страниц
                    ORDER BY p.created_at DESC, p.id DESC
                    LIMIT ?                                 -- limit + 1
            ) lp
        WHERE s.follower_id = ?
        ORDER BY lp.created_at DESC, lp.id DESC
        LIMIT ?                                             -- limit + 1
)
SELECT  p.id,
        p.author_id,
        p.title,
        p.content,
        p.status,
        p.created_at,
        p.updated_at
    FROM page
        JOIN posts p ON p.id = page.id
    ORDER BY p.created_at DESC, p.id DESC
```

- **`LATERAL`** разрешает подзапросу во `FROM` ссылаться на строку `subscriptions` слева: он выполняется для каждой подписки, как тело цикла. **`CROSS JOIN`** — потому что условие связи (`p.author_id = s.followed_id`) уже внутри подзапроса; авторы без опубликованных постов просто выпадают.
- **`LIMIT` внутри `LATERAL`** — главное: первые `limit` постов ленты обязательно входят в объединение первых `limit` постов каждого автора, поэтому ограничение по автору ничего не теряет. Объём работы — `подписки × (limit + 1)` записей индекса, независимо от числа постов и глубины страницы.
- **Двухфазное чтение:** подзапрос берёт из индекса только `id` и `created_at` (Index Only Scan, без чтения таблицы); `content` и остальные колонки читаются по первичному ключу только для итоговых строк.
- **`limit + 1`:** лишняя строка не возвращается, её наличие означает «есть следующая страница» — без отдельного `COUNT`.
- `p.status = 'PUBLISHED'` должен стоять в запросе дословно: только так планировщик выбирает частичный индекс.

### Индексы

- `idx_posts_published_author_created ON posts (author_id, created_at DESC, id DESC) WHERE status = 'PUBLISHED'` (changeset `008`) — частичный: удалённых постов в нём нет; в нём есть всё для отбора, поэтому Index Only Scan (`Heap Fetches: 0` после `VACUUM`). Условие курсора `(created_at, id) < (?, ?)` становится условием индекса (`Index Cond: ... ROW(created_at, id) < ROW(...)`), а не фильтром.
- `uq_subscriptions_users (follower_id, followed_id)` (ограничение уникальности `subscriptions`) — подписки читателя, тоже Index Only Scan.

## Страницы: курсор `(created_at, id)`

- `findFeed(followerId, limit)` — первая страница; `findFeedAfter(followerId, after, limit)` — посты строго после `after` в порядке ленты.
- Ответ — `FeedPageResponse(posts, next)`: `next` — курсор следующей страницы (позиция последнего поста страницы), пустой — постов больше нет. Пустая лента — пустые `posts` и `next`.
- `limit` — от 1 до `FeedRepository.MAX_LIMIT` (100): стоимость страницы растёт с `limit`, клиент не должен её раздувать. Иначе — `IllegalArgumentException`; `after == null` — `NullPointerException`; обе проверки — до обращения к БД.
- **Курсор берётся только из ответа** (`next`): `TIMESTAMPTZ` хранит микросекунды, а `Instant` из `Clock` может содержать наносекунды — собранный вручную курсор может не совпасть ни с одной строкой.
- Живая лента не сдвигает страницы: новый пост выше курсора — появится при новом чтении первой страницы, а не дублем на следующей; удаление поста (в том числе самого поста курсора) и отписка не вызывают пропусков — курсор задаёт позицию, а не номер строки.
- Перехода «на страницу N» нет: для бесконечной прокрутки он не нужен.

## История решения: почему не `LIMIT ? OFFSET ?`

Первая версия ленты (задача 41215) использовала `subscriptions JOIN posts ... ORDER BY ... LIMIT ? OFFSET ?`. Замер (PostgreSQL 17, 2 млн постов, читатель подписан на 1 000 авторов, страница 20):

| Запрос | Что делает PostgreSQL | Время |
| --- | --- | --- |
| `JOIN` + `OFFSET 0` | читает все посты подписок (380 тыс.) или всю таблицу (`Seq Scan`), сортирует их | ~320 мс |
| `JOIN` + `OFFSET 10000` | то же + сортировка на диск (`external merge`, ~140 МБ) | ~400 мс |
| текущий запрос, первая страница | `Index Only Scan` по 21 записи с автора, 20 чтений по `id` | ~11–29 мс |
| текущий запрос, страница после 10 000 записей | то же, курсор — условие индекса | ~11 мс |

Причины отказа:

- **`OFFSET` не пропускает строки:** для страницы `N` база собирает и сортирует `N + limit` строк и выбрасывает `N` — глубокие страницы дорожают линейно.
- **На живой ленте страницы «плывут»:** новый пост сверху сдвигает всё вниз (дубль на следующей странице), удаление или отписка — вверх (пропуск).
- **`JOIN` читает все посты всех подписок:** индекс упорядочен по дате внутри автора, а не по всей ленте, поэтому `ORDER BY ... LIMIT` по объединению авторов требует прочитать и отсортировать всё. Время растёт с историей авторов. `WHERE author_id IN (список авторов)` вместо `JOIN` даёт то же самое: ускоряет только ограничение «не больше `limit` с автора».
- **`status` не был в индексе:** каждый пост проверялся по таблице, удалённые читались зря; `content` читался для сотен тысяч строк.

## Профиль нагрузки и выбор решения

Ожидаемый профиль (`docs/md/task/41215-2/descr.md`): пользователей — несколько миллионов; читатель обычно подписан не больше чем на 200 авторов (типично 20–200); у отдельных авторов — до нескольких миллионов подписчиков.

- **Стоимость страницы — `подписки × limit` записей индекса** и не зависит ни от числа постов, ни от числа подписчиков автора. Число пользователей почти не влияет на время одного запроса (поиск в B-tree логарифмический); оно увеличивает число запросов в секунду.
- **Популярные авторы ленте не мешают:** миллионы читателей берут из индекса одни и те же первые записи диапазона автора — эти страницы постоянно в памяти. Пост популярного автора — один `INSERT`, удаление — один `UPDATE`, изменение сразу видно во всех лентах.
- **Худший случай страницы:** 200 подписок × 101 ≈ 20 000 записей индекса (~15 мс в замере).

Замер на данных `src/main/resources/db/changes/0091-sql-examples.sql` (2 млн постов, прогретый кеш, страница 21 строка):

| Вариант | 202 подписки | 1 003 подписки |
| --- | --- | --- |
| A. `WHERE author_id = ANY(список авторов)` | — | 381 287 постов, 88 мс |
| B. `JOIN subscriptions` + `ORDER BY` (с частичным индексом) | 76 641 постов, 23 мс | 381 287 постов, 109 мс |
| **C. `subscriptions CROSS JOIN LATERAL` (текущий)** | **4 242 записи индекса, 2,5 мс** | **21 063, 15 мс** |
| D. список авторов отдельным запросом + `unnest(?::uuid[]) CROSS JOIN LATERAL` | 4 242, 2,1 мс | 21 063, 11 мс |

C и D по нагрузке на БД равны; выбран C: один запрос, без изменений API и зависимостей модулей, ценой чтения таблицы `subscriptions` чужого модуля (согласованное исключение, `docs/architecture.md`). D нужен, если `posts` и `subscriptions` разойдутся по разным базам или сервисам: список авторов берётся через API модуля `subscriptions`, меняется только источник авторов во `FROM`, часть с `LATERAL` остаётся.

## Развитие

- **Готовая лента на запись (fan-out on write) при этом профиле не подходит.** Она выигрывает у читателя с тысячами подписок (у нас — до 200, сборка при чтении стоит 2–15 мс), а проигрывает на авторах с миллионами подписчиков: каждый их пост — миллионы вставок в таблицу лент, удаление — миллионы удалений. Возвращаться к ней стоит, только если типичный читатель будет подписан на тысячи авторов.
- **При росте числа запросов,** по порядку:
  1. реплики PostgreSQL для чтения ленты;
  2. кеш последних постов **автора** (ключ — автор; инвалидация — событием публикации или удаления его поста: один ключ, сколько бы ни было подписчиков); первая страница собирается слиянием до 200 таких списков. Кеш готовой страницы читателя — только с коротким TTL: сбрасывать его событиями нельзя, пост популярного автора сбросил бы миллионы ключей;
  3. кеш списка подписок (для варианта D);
  4. шардирование `posts` по `author_id` (нужен вариант D); шард популярного автора разгружают реплики и кеш.
- **Подгрузка новых постов на первой странице** (опрос раз в 0,5–2 минуты) — тот же запрос с курсором вверх, `(created_at, id) > (верхний пост страницы)`: ~1 мс на читателя с 200 подписками. Дорого их число, поэтому опрос идёт в кеш времени последнего поста автора, отвечает «есть ли новые», а не отдаёт посты, и берёт запас ~10 секунд (пост может закоммититься позже своего `created_at`). Подробно — `docs/md/task/41215-2/README.md`, раздел 4.2.
