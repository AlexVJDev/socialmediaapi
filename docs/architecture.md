# Архитектура

Базовый пакет: `ru.job4j.socialmediaapi` (главный класс `SocialMediaApiApplication`).
Приложение — модульный монолит на Spring Modulith; модуль — прямой подпакет базового
пакета с `@ApplicationModule` в `package-info.java`
(`spring.modulith.detection-strategy: explicitly-annotated` в `application.yml`).

Документ задаёт правила: куда положить класс и какие зависимости допустимы.
Запуск и окружение — в `README.md`, команды и процесс — в `CLAUDE.md`.

## Модули

| Модуль | Ответственность | `allowedDependencies` | Публичный `api` | Статус |
| --- | --- | --- | --- | --- |
| `subscriptions` | Подписки читателя на автора | `{}` | `Subscriptions` (`subscribeIfAbsent`, `unsubscribe`) | перенесён |
| `posts` | Посты и лента подписчика | `{}` | нет | перенесён |
| `friendships` | Заявки в друзья и дружба | `subscriptions::api` | нет | перенесён |
| `system` | Служебные эндпоинты (`/api/ping`) | `{}` | нет | перенесён |

Граф зависимостей: `friendships → subscriptions`; циклов нет.

**Исключение из правила «не читать чужие таблицы».** SQL ленты в `posts` соединяет
таблицу `subscriptions` модуля `subscriptions` (`subscriptions JOIN posts`): одна выборка
с сортировкой и пагинацией (`docs/process/Feed.md`). В Java-коде `posts` от `subscriptions`
не зависит. Других чтений чужих таблиц нет; новое — только по согласованию и с записью здесь.
При росте нагрузки лента переходит на собственную проекцию подписок, наполняемую событиями
`subscriptions`.

## Архитектура модуля

Модуль объединяет связанные бизнес-сценарии, правила и данные. Взаимодействие
с другими модулями происходит через публичные контракты. Внутренняя организация
следует гексагональной архитектуре: бизнес-логика отделена от способов запуска
сценариев, хранения данных и внешних интеграций.

### Слои и ответственность

| Слой | Что может находиться |
| --- | --- |
| `api` | Публичные интерфейсы, модели и события, необходимые другим модулям. |
| `internal.domain` | Бизнес-модели, правила, состояния, переходы и доменные ошибки. |
| `internal.application` | Прикладные сценарии, координация операций, границы транзакций, модели сценариев и порты. |
| `internal.infrastructure` | Входные и выходные адаптеры: контроллеры, слушатели, работа с хранилищем, интеграции и технические настройки. |

Подпакеты создаются по необходимости и группируются по ответственности.
Не нужно создавать пустые слои или отдельный интерфейс для каждого класса.

### Публичный контракт — `api`

Описывает возможности модуля, которыми могут пользоваться другие модули.
Потребителю должно быть достаточно этого контракта, чтобы вызвать операцию
или обработать событие без знания внутреннего устройства модуля.

Здесь размещаются интерфейсы доступных операций, модели их входных данных
и результатов, публичные события, перечисления и ошибки, которые потребитель
должен уметь обрабатывать. В контракт включается только необходимая внешним
потребителям информация.

Реализация операций, доступ к хранилищу и техническая конфигурация остаются
в `internal`. Вспомогательный класс не становится частью `api` только потому,
что его удобно переиспользовать. Изменение публичного контракта требует учитывать
его потребителей.

Операция `api` выполняется в транзакции вызывающего модуля (`Propagation.REQUIRED`):
так создание заявки в друзья и подписка отправителя остаются атомарными.

### Бизнес-правила — `internal.domain`

Описывает смысл бизнес-объектов и правила, которые должны соблюдаться независимо
от способа запуска сценария. Здесь находятся доменные модели, объекты-значения,
допустимые состояния и переходы, расчёты, политики и доменные ошибки.

Доменная логика проверяет допустимость действий над бизнес-объектом и сохраняет
его инварианты. Например, правило допустимого перехода состояния относится
к domain, а загрузка объекта перед этим переходом — к application.

Доменный слой работает с переданными ему данными. Он не обрабатывает HTTP-запросы,
не вызывает внешние сервисы и не определяет способ сохранения результата.
Доменная модель строится вокруг бизнес-смысла и не обязана повторять модель
хранения или формат внешнего сообщения. Ограничения БД (CHECK, UNIQUE) только
подстраховывают инварианты домена.

### Прикладные сценарии — `internal.application`

Организует выполнение конкретной задачи: получает необходимые данные,
применяет доменные правила, вызывает внешние операции через порты, сохраняет
результат и публикует события. Здесь определяются последовательность действий
и границы транзакций (`@Transactional` — на сценарии).

В слое размещаются сценарии, реализации публичных интерфейсов модуля, прикладные
сервисы, команды и запросы, результаты операций, порты и ошибки сценариев.
Общие операции выделяются в отдельный сервис, когда у них есть самостоятельная
ответственность или несколько потребителей.

Сценарий — класс в `usecase`, один сценарий — один класс; имя — глагол + сущность
без суффикса (`CreateFriendshipOffer`). Отдельный интерфейс входного порта не создаётся.
Время берётся из бина `Clock`, а не из `Instant.now()`.

Порт описывает, какие данные или действия нужны сценарию: прочитать и сохранить
бизнес-объект, получить внешние сведения, отправить документ. Он не задаёт
протокол вызова, структуру таблицы или тип конкретного клиента. Реализация порта
находится в infrastructure. Порты хранения называются `*Repository`
(`SubscriptionRepository`); в `application.port` лежат только интерфейсы,
их модели (`*Request` / `*Response`) — в `application.port.model`.

Прикладной слой решает, когда выполнить операцию и как связать её с остальными
шагами. Правила допустимости бизнес-состояния он делегирует domain, а технический
способ выполнения операции — адаптеру. Модели сценариев не содержат модели
хранения или транспортные объекты.

### Адаптеры и технические детали — `internal.infrastructure`

Связывает сценарии с окружением приложения. Здесь находятся реализации портов
и точки входа, через которые запускается прикладная логика.

- **Входные адаптеры:** контроллеры, слушатели событий. Принимают входные данные,
  проверяют их формат, преобразуют в модели сценария и вызывают его.
- **Хранение (JDBC):** `*Row` — записи, повторяющие строку таблицы (не `*Entity`:
  в DDD сущность — это доменный объект); `*PersistenceAdapter` — реализация порта
  на `JdbcTemplate` с нативным SQL; MapStruct-мапперы port model ↔ Row.
- **Безопасность:** реализация порта текущего пользователя (планируется Keycloak).
- **Конфигурация:** создание и связывание компонентов, параметры подключений.

Адаптер отвечает за техническое выполнение операции. Он не определяет
бизнес-последовательность действий и не дублирует правила домена.
Входной адаптер обращается к сценарию, а не напрямую к хранилищу в обход
прикладного слоя.

Правила хранения:
- **Нет check-then-act.** Запись не предваряется чтением, решающим, писать ли:
  уникальность — ключом в `INSERT`, владелец и состояние — в `WHERE` того же
  `UPDATE` / `DELETE`.
- Адаптер переводит в ошибку контракта порта только нарушение уникального ключа
  (`*AlreadyExistsException` в `application.exception`: это не нарушение доменного
  правила, а ответ хранилища «запись уже есть»), различая его по имени констрейнта. Прочие
  `DataIntegrityViolationException` пробрасываются как есть → `500 INTERNAL_ERROR`.
- Разбор ошибки PostgreSQL (`PostgresErrors`) — копия в `persistence.adapter` каждого
  модуля, которому она нужна. Перенос в `shared` — отдельным решением, если копий станет много.

### Как размещать проверки, преобразования и ошибки

Их слой определяется смыслом операции, а не названием класса.

| Ответственность | Где размещать |
| --- | --- |
| Проверка формата входного сообщения и преобразование транспортных данных | Во входном инфраструктурном адаптере |
| Проверка условий выполнения сценария и сборка его результата | В application |
| Проверка бизнес-инвариантов, допустимости состояния и расчёт по бизнес-правилам | В domain |
| Преобразование моделей хранения | В выходном инфраструктурном адаптере (`persistence.mapper`) |

Ошибки определяются в слое, которому принадлежит нарушенное правило или
контракт. Технические ошибки преобразуются на границе адаптера, а ошибки,
которые должен обрабатывать другой модуль, описываются в публичном `api`.
HTTP-коды ошибок модуля — в его `infrastructure.web`: обработчик `*ExceptionHandler`
(`@RestControllerAdvice(assignableTypes = <контроллеры модуля>)`, `@Order(Ordered.HIGHEST_PRECEDENCE)`)
и перечисление `web.error.ErrorCode`. Обработчик модуля ограничен своими контроллерами, поэтому
коды одного модуля не достаются эндпоинтам другого. Общий ответ `500 INTERNAL_ERROR` —
`shared.exception.GlobalExceptionHandler` (`@Order(Ordered.LOWEST_PRECEDENCE)`, срабатывает после
обработчиков модулей); тело ошибки `{code, message}` — `shared.web.ErrorResponse`.

## Типовая структура файлов и пакетов

Ниже показаны используемые пакеты внутри `src/main/java/ru/job4j/socialmediaapi/<module>`.
Это ориентир для размещения файлов, а не обязательный шаблон: создаются только нужные
части. Имена с `*` обозначают примеры назначения файлов.

```text
<module>/
├── package-info.java                  # @ApplicationModule + allowedDependencies
├── api/                              # Публичный Java-контракт
│   ├── *.java                        # Интерфейсы публичных операций (@NamedInterface("api"))
│   ├── model/                        # Публичные запросы, результаты и enum
│   ├── event/
│   │   ├── package-info.java         # @NamedInterface("events")
│   │   └── *Event.java               # В том числе события для @ApplicationModuleListener
│   └── exception/                    # Ошибки, доступные потребителям контракта
└── internal/                         # Закрытая реализация модуля
    ├── domain/
    │   ├── model/                    # Агрегаты, значения, статусы
    │   ├── policy/                   # Бизнес-правила и переходы состояний
    │   └── exception/                # Нарушения доменных правил
    ├── application/
    │   ├── usecase/                  # Один сценарий — один класс (CreateFriendshipOffer)
    │   ├── service/                  # Реализации api и общие прикладные операции
    │   ├── model/                    # *Command, *Query, *Result
    │   ├── port/                     # Интерфейсы портов (*Repository)
    │   │   └── model/                # *Request / *Response портов
    │   ├── mapper/                   # Domain → port model, port model → Result
    │   └── exception/                # Ошибки сценариев и контрактов портов
    └── infrastructure/
        ├── web/
        │   ├── *Controller.java      # HTTP-точки входа в сценарии
        │   ├── *ExceptionHandler.java # Ошибки модуля → HTTP (@RestControllerAdvice)
        │   ├── request/              # *WebRequest, проверка формата (Bean Validation)
        │   ├── response/             # *WebResponse
        │   ├── error/                # ErrorCode модуля
        │   └── mapper/               # *WebMapper
        ├── persistence/
        │   ├── row/                  # *Row — запись = строка таблицы
        │   ├── adapter/              # *PersistenceAdapter — реализация порта на JdbcTemplate
        │   └── mapper/               # *PersistenceMapper
        ├── event/                    # Обработчики событий, вызывающие сценарии
        ├── security/                 # Порт текущего пользователя (Keycloak)
        └── config/                   # @Configuration модуля
```

Папки `model`, `mapper` и `exception` относятся к своему слою или адаптеру.
MapStruct-мапперы лежат в `mapper/` своего слоя или адаптера, а не в `service/`,
`adapter/` или корне `web/` (правила маппинга — раздел «Маппинг» в `CLAUDE.md`).
Публичные и внутренние модели разделяются по контрактам; создавать копию каждой
модели для каждого слоя без необходимости не нужно.

Тесты располагаются в `src/test/java` и повторяют пакет проверяемого кода.
Архитектурный тест, проверяющий общие правила всех модулей, лежит в `architecture`.
Для web-endpoint’ов с URL `/internal/**` отдельные контроллерные тесты по умолчанию
не создаются.

## Зависимости и границы

- Другие модули используют только `api`. Внутренняя реализация модуля закрыта.
- Публичные контракты не зависят от `internal` и не раскрывают детали реализации.
- Доменный слой не зависит от прикладного и инфраструктурного слоёв.
- Прикладной слой использует доменные правила; для хранилища и контекста
  безопасности он определяет порты.
- Порт описывает потребность сценария и принадлежит потребляющему модулю.
  Инфраструктурный адаптер реализует этот контракт.
- Входные адаптеры принимают вызов и передают его прикладному сценарию.
- Модели публичных контрактов и сценариев независимы от форматов транспорта
  и хранения. Преобразования выполняются на соответствующих границах.
- `*Row` не выходят за пределы `infrastructure.persistence`.
- Общие технические компоненты (`shared`) не управляют бизнес-сценариями модулей.

## События

Событие принадлежит модулю, который определяет его контракт. Публичные события
размещаются в `api.event` и содержат только данные, необходимые потребителям.

**Типы событий, принимаемые методами с `@ApplicationModuleListener`, всегда
размещаются в `<module>.api.event` или его подпакетах.** Сами слушатели относятся
к инфраструктуре и делегируют выполнение прикладным сценариям.
Сейчас событий в проекте нет; при появлении надёжной доставки подключается
`spring-modulith-starter-jdbc` с таблицей `event_publication` (миграцией Liquibase).

## Архитектурные тесты

Тест: `src/test/java/ru/job4j/socialmediaapi/architecture/ApplicationModulesTest.java`.

| Правило теста | Формулировка |
| --- | --- |
| `verifiesModuleStructure` | Spring Modulith: нет циклов, межмодульные обращения только к `api` и в рамках `allowedDependencies` |
| `verifiesLayerDependenciesInAllModules` | domain → ничего; application → domain; infrastructure → application, domain |
| `persistenceRowsBelongToPersistence` | Классы `*Row` только в `infrastructure.persistence.row` |
| `controllersBelongToWebInfrastructure` | `@Controller`/`@RestController` только в `infrastructure.web` |
| `moduleClassesBelongToArchitecturalLayers` | Каждый класс модуля лежит в `api` или `internal.{domain,application,infrastructure}` |
| `domainHasOnlyBusinessDependencies` | domain зависит только от domain, `api`, `shared.exception`, Java, Lombok |
| `publicApiDoesNotExposeImplementation` | `api` не зависит от `internal`, моделей хранения, HTTP |
| `webAdaptersUseApplicationScenarios` | web не обращается к persistence и `application.port` |
| `applicationUsesPortsForTechnicalOperations` | application не зависит от JDBC, драйвера PostgreSQL, Spring DAO, HTTP |

Правила применяются ко всем модулям одинаково; персональные исключения для классов
и слоёв в тесте не используются. При добавлении модуля отдельный архитектурный тест
не создаётся. Разрешённые связи между модулями задаются в `package-info.java`.
Правило размещения событий `@ApplicationModuleListener` в `api.event` и исключение
для SQL ленты автоматически не проверяются — их контролирует ревью.
Конкретные бизнес-обязанности проверяются поведенческими тестами сценариев.

## Общее ядро `shared`

`shared` — не модуль Modulith, а общее техническое ядро. Оно не зависит от бизнес-модулей
и не содержит бизнес-логики.

| Пакет | Содержимое |
| --- | --- |
| `shared.config` | Сквозная техническая конфигурация (`ClockConfiguration` — бин `Clock`, UTC) |
| `shared.web` | Общее тело ошибки `ErrorResponse(code, message)` |
| `shared.exception` | Общий обработчик ошибок `GlobalExceptionHandler`: непредвиденная `DataIntegrityViolationException` → `500 INTERNAL_ERROR` |

В `shared` запрещены модели хранения, репозитории, контроллеры, задания по расписанию,
бизнес-порты и их адаптеры. Такой код оформляется отдельным модулем.

## Переходный период

Удалить раздел после завершения рефакторинга (`docs/refactoring-kit/02-refactoring-guide.md`,
этап 4).

Код в legacy-пакетах ниже ещё не перенесён в модули. Он обращается к модулям только
через их `api`. Новый код в эти пакеты не добавляется. Список совпадает
с `LEGACY_PACKAGES` в архитектурном тесте.

Legacy-пакетов не осталось (`LEGACY_PACKAGES` пуст); раздел и константа удаляются на этапе 4.
