# 41215-2. Лента при очень большом числе пользователей и запросов

Источник: `descr.md`. Нужно переделать выдачу ленты (`FeedRepository.findFeed`) так, чтобы она выдерживала очень много пользователей и запросов. Исходная точка — текущий запрос из `FeedPersistenceAdapter`:

```sql
SELECT p.id, p.author_id, p.title, p.content, p.status, p.created_at, p.updated_at
FROM subscriptions s
JOIN posts p ON p.author_id = s.followed_id
WHERE s.follower_id = ?
  AND p.status = 'PUBLISHED'
ORDER BY p.created_at DESC, p.id DESC
LIMIT ? OFFSET ?;
```

**Предложение в двух словах.** Этап 1 (делаем сейчас, только SQL, индекс и контракт порта): курсорная пагинация вместо `OFFSET`, частичный индекс по `PUBLISHED`, выборка «не больше `limit` постов с каждого автора» через `LATERAL` и чтение `content` только для итоговой страницы. Стоимость запроса перестаёт зависеть от числа постов и глубины страницы. Этап 2 (описан как развитие, не реализуется): готовая лента на запись (fan-out on write) через события модулей — для пользователей с тысячами подписок и авторов с миллионами подписчиков.

## 1. Почему текущий запрос не масштабируется

Замер на PostgreSQL 17 (отдельный временный контейнер): 5 000 авторов × 400 постов = 2 млн постов (~5 % `DELETED`, `content` 300 байт), читатель подписан на 1 000 авторов, страница 20.

| Запрос | Что делает PostgreSQL | Прочитано страниц (8 КБ) | Время |
| --- | --- | --- | --- |
| текущий, `OFFSET 0` | `Parallel Seq Scan` всех 2 млн постов → `Hash Join` → top-N sort 380 тыс. строк | ~100 000 (~800 МБ) | ~320 мс |
| текущий, `OFFSET 10000` | то же + сортировка 10 020 строк **на диск** (`external merge`, ~140 МБ temp) | ~100 000 + temp | ~400 мс |
| текущий + частичный индекс (п. 2.2) | `Index Only Scan` всех 380 тыс. постов подписок → top-N sort | — | ~40 мс (кеш прогрет) |
| **предлагаемый**, первая страница | `Index Only Scan` по 20 записей с автора (20 000 строк) → top-20 → 20 чтений по `id` | ~3 250 | ~29 мс (холодный кеш) |
| **предлагаемый**, страница после 10 000 записей | то же, курсор — условие индекса | ~3 240 | ~11 мс |

Результаты предлагаемого запроса совпадают с текущим строка в строку (проверено `EXCEPT` для страницы после 10 000 записей).

Причины:

1. **`OFFSET` не пропускает строки.** Чтобы отдать страницу `N`, база собирает и сортирует `N + limit` строк и выбрасывает `N`. Глубокие страницы дорожают линейно, сортировка уходит на диск. Плюс страницы «плывут» на живой ленте: новый пост сдвигает всё вниз (дубль), удаление и отписка — вверх (пропуск) — описано в `docs/process/Feed.md`.
2. **Читаются все посты всех подписок.** `ORDER BY` по объединению авторов нельзя взять из индекса `(author_id, created_at DESC, id DESC)` одним проходом: индекс упорядочен внутри автора, а не по всей ленте. PostgreSQL читает все посты всех подписок (или всю таблицу) и сортирует. Стоимость растёт с числом постов — то есть со временем жизни сервиса.
3. **`status` не в индексе.** Каждый пост проверяется в таблице (heap), index-only scan невозможен, удалённые посты читаются зря.
4. **`content` (TEXT) читается для сотен тысяч строк**, хотя нужен только для 20 строк страницы.

## 2. Этап 1 — что предлагается сделать сейчас

### 2.1. Курсорная (keyset) пагинация вместо `OFFSET`

Следующая страница запрашивается не номером, а позицией последнего показанного поста — парой `(created_at, id)`. Это уже описанное в `Feed.md` развитие, теперь оно становится основной реализацией.

- `(p.created_at, p.id) < (?, ?)` — сравнение строк PostgreSQL; проверено, что оно становится условием индекса (`Index Cond: ... ROW(created_at, id) < ROW(...)`), а не фильтром.
- `id` в курсоре нужен по той же причине, что и в `ORDER BY`: у нескольких постов может быть одинаковый `created_at`.
- Новые посты не сдвигают следующие страницы (они выше курсора — появятся при обновлении первой страницы); удаление и отписка не вызывают пропусков.
- Курсор берётся только из строки, прочитанной из БД: `TIMESTAMPTZ` хранит микросекунды, а `Instant` из `Clock` может содержать наносекунды — «самодельный» курсор с наносекундами сломал бы сравнение.
- Страница с переходом «на номер N» больше не поддерживается — для бесконечной прокрутки она не нужна.

### 2.2. Частичный индекс по опубликованным постам

```sql
CREATE INDEX idx_posts_published_author_created
    ON posts (author_id, created_at DESC, id DESC)
    WHERE status = 'PUBLISHED';
```

- Удалённые посты в индекс не попадают: фильтр `status = 'PUBLISHED'` выполняется самим индексом.
- В индексе есть всё, что нужно для отбора (`author_id`, `created_at`, `id`), — `Index Only Scan` без чтения таблицы (`Heap Fetches: 0` при свежем `VACUUM`).
- Старый `idx_posts_author_created` полностью перекрывается новым (все запросы `posts` по автору и так читают только `PUBLISHED`) — предлагается удалить его в той же миграции, чтобы не платить за лишний индекс на каждой записи.
- Миграция — новый changeset `010` в отдельном файле индексов (`007`/`008` не меняются: они уже применены). На рабочей базе индекс создаётся `CREATE INDEX CONCURRENTLY` (в Liquibase — `runInTransaction:false`), чтобы не блокировать запись в `posts`; в учебном проекте достаточно обычного `CREATE INDEX`.

### 2.3. Не больше `limit` постов с каждого автора (`LATERAL`)

Глобальные первые `limit` постов ленты обязательно входят в объединение первых `limit` постов каждого автора. Поэтому достаточно для каждой подписки взять из индекса `limit` верхних постов (`LIMIT` внутри `LATERAL`), объединить и отсортировать. Объём работы — `подписки × limit` записей индекса, **независимо от числа постов и глубины страницы**.

### 2.4. Двухфазное чтение: сначала ключи, потом содержимое

Внутренний подзапрос отбирает только `id` и `created_at` (из индекса). Колонки страницы, включая `content`, читаются по первичному ключу только для итоговых `limit` строк.

### 2.5. Итоговый запрос

Первая страница — тот же запрос без условия курсора (в адаптере две SQL-константы, без склейки строк).

```sql
WITH page AS (
    SELECT lp.id, lp.created_at
    FROM subscriptions s
    CROSS JOIN LATERAL (
        SELECT p.id, p.created_at
        FROM posts p
        WHERE p.author_id = s.followed_id
          AND p.status = 'PUBLISHED'
          AND (p.created_at, p.id) < (?, ?)          -- только для следующих страниц
        ORDER BY p.created_at DESC, p.id DESC
        LIMIT ?                                     -- limit + 1
    ) lp
    WHERE s.follower_id = ?
    ORDER BY lp.created_at DESC, lp.id DESC
    LIMIT ?                                         -- limit + 1
)
SELECT p.id, p.author_id, p.title, p.content, p.status, p.created_at, p.updated_at
FROM page
JOIN posts p ON p.id = page.id
ORDER BY p.created_at DESC, p.id DESC;
```

`limit + 1` — чтобы без отдельного `COUNT` узнать, есть ли следующая страница: лишняя строка не возвращается, а её наличие означает «курсор следующей страницы = последний пост страницы».

### 2.6. Ограничение размера страницы

`limit` ограничивается сверху (предлагается `100`): стоимость запроса — `подписки × limit`, клиент не должен её раздувать. `limit <= 0` или `> 100` → `IllegalArgumentException` до обращения к БД (как сейчас для `limit <= 0`).

### 2.7. Изменения в коде (модуль `posts`)

Пакеты — относительно `ru.job4j.socialmediaapi.posts.internal`. Сервиса и REST у ленты пока нет, поэтому старый метод с `offset` заменяется, а не сохраняется рядом.

| Где | Что |

### 2.8. Тесты

- `FeedPersistenceAdapterTest` — существующие сценарии (подписка/отписка/`DELETED`/взаимная дружба/чужие авторы) переводятся на новые методы. Новые:

## 3. Что остаётся ограничением после этапа 1

- **Стоимость ~ `подписки × limit`.** 1 000 подписок — ~20 000 записей индекса на запрос (замер выше — 11–29 мс). У пользователя с 10 000+ подписок это уже сотни тысяч строк на каждый скролл.
- **Каждый запрос ленты — работа БД.** При очень большом числе читателей нагрузка на чтение растёт линейно; кеша нет.
- **Чтение чужой таблицы `subscriptions`** остаётся.

Для «очень-очень много» этого достаточно как первый шаг (на порядки лучше текущего, без новой инфраструктуры), но не как конечное состояние.

## 4. Этап 2 — развитие (не реализуется в этой задаче)

**Готовая лента на запись (fan-out on write) с гибридом для «звёзд».** Направление уже записано в `docs/architecture.md` («лента переходит на собственную проекцию подписок, наполняемую событиями `subscriptions`»).

- Таблица `feed_items (follower_id, created_at, post_id, author_id)`, первичный ключ `(follower_id, created_at DESC, post_id DESC)`. Чтение страницы — один диапазон индекса одного пользователя: `WHERE follower_id = ? AND (created_at, post_id) < (?, ?) LIMIT ?`, стоимость не зависит от числа подписок.
- Наполняется событиями: `posts.api.event.PostPublished` / `PostDeleted`, `subscriptions.api.event.Subscribed` / `Unsubscribed` (типы — в `api.event`, слушатели `@ApplicationModuleListener` — в `infrastructure.event`). Надёжная доставка — `spring-modulith-starter-jdbc` с таблицей `event_publication` (миграция Liquibase). Лента становится eventually consistent: пост появляется у подписчиков через доли секунды.
- **Гибрид:** авторы с огромным числом подписчиков (порог, например, 10 000) в `feed_items` не размножаются — их посты подмешиваются при чтении запросом этапа 1 (подписок на «звёзд» у читателя мало, `LATERAL` по ним дешёв).
- В `feed_items` хранится только «хвост» (например, последние 1 000 записей или 30 дней на пользователя); глубже — запрос этапа 1.
- После перехода `posts` больше не читает таблицу `subscriptions` — исключение из `architecture.md` снимается.

Сопутствующее при дальнейшем росте: кеш первой страницы (Redis) с инвалидацией по тем же событиям, реплики PostgreSQL для чтения ленты, секционирование `posts` по `created_at`.
