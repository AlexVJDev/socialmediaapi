# 41215-2. Лента при очень большом числе пользователей и запросов

Источник: `descr.md`. Нужно переделать выдачу ленты (`FeedRepository.findFeed`) так, чтобы она выдерживала очень много пользователей и запросов. Исходная точка — текущий запрос из `FeedPersistenceAdapter`:

```sql
SELECT p.id, p.author_id, p.title, p.content, p.status, p.created_at, p.updated_at
FROM subscriptions s
JOIN posts p ON p.author_id = s.followed_id
WHERE s.follower_id = ?
  AND p.status = 'PUBLISHED'
ORDER BY p.created_at DESC, p.id DESC
LIMIT ? OFFSET ?;
```

**Предложение в двух словах.** Этап 1 (делаем сейчас, только SQL, индекс и контракт порта): курсорная пагинация вместо `OFFSET`, частичный индекс по `PUBLISHED`, выборка «не больше `limit` постов с каждого автора» через `LATERAL` и чтение `content` только для итоговой страницы. Стоимость запроса перестаёт зависеть от числа постов и глубины страницы. Этап 2 (описан как развитие, не реализуется): при ожидаемом профиле (у читателя до 200 подписок, у популярных авторов — миллионы подписчиков) — реплики для чтения и кеш последних постов автора; готовая лента на запись (fan-out on write) при таком профиле вредна: пост популярного автора превращался бы в миллионы вставок (разделы 3.1, 4).

## 1. Почему текущий запрос не масштабируется

Замер на PostgreSQL 17 (отдельный временный контейнер): 5 000 авторов × 400 постов = 2 млн постов (~5 % `DELETED`, `content` 300 байт), читатель подписан на 1 000 авторов, страница 20.

| Запрос | Что делает PostgreSQL | Прочитано страниц (8 КБ) | Время |
| --- | --- | --- | --- |
| текущий, `OFFSET 0` | `Parallel Seq Scan` всех 2 млн постов → `Hash Join` → top-N sort 380 тыс. строк | ~100 000 (~800 МБ) | ~320 мс |
| текущий, `OFFSET 10000` | то же + сортировка 10 020 строк **на диск** (`external merge`, ~140 МБ temp) | ~100 000 + temp | ~400 мс |
| текущий + частичный индекс (п. 2.2) | `Index Only Scan` всех 380 тыс. постов подписок → top-N sort | — | ~40 мс (кеш прогрет) |
| **предлагаемый**, первая страница | `Index Only Scan` по 20 записей с автора (20 000 строк) → top-20 → 20 чтений по `id` | ~3 250 | ~29 мс (холодный кеш) |
| **предлагаемый**, страница после 10 000 записей | то же, курсор — условие индекса | ~3 240 | ~11 мс |

Результаты предлагаемого запроса совпадают с текущим строка в строку (проверено `EXCEPT` для страницы после 10 000 записей).

Причины:

1. **`OFFSET` не пропускает строки.** Чтобы отдать страницу `N`, база собирает и сортирует `N + limit` строк и выбрасывает `N`. Глубокие страницы дорожают линейно, сортировка уходит на диск. Плюс страницы «плывут» на живой ленте: новый пост сдвигает всё вниз (дубль), удаление и отписка — вверх (пропуск) — описано в `docs/process/Feed.md`.
2. **Читаются все посты всех подписок.** `ORDER BY` по объединению авторов нельзя взять из индекса `(author_id, created_at DESC, id DESC)` одним проходом: индекс упорядочен внутри автора, а не по всей ленте. PostgreSQL читает все посты всех подписок (или всю таблицу) и сортирует. Стоимость растёт с числом постов — то есть со временем жизни сервиса.
3. **`status` не в индексе.** Каждый пост проверяется в таблице (heap), index-only scan невозможен, удалённые посты читаются зря.
4. **`content` (TEXT) читается для сотен тысяч строк**, хотя нужен только для 20 строк страницы.

## 2. Этап 1 — что предлагается сделать сейчас

### 2.1. Курсорная (keyset) пагинация вместо `OFFSET`

Следующая страница запрашивается не номером, а позицией последнего показанного поста — парой `(created_at, id)`. Это уже описанное в `Feed.md` развитие, теперь оно становится основной реализацией.

- `(p.created_at, p.id) < (?, ?)` — сравнение строк PostgreSQL; проверено, что оно становится условием индекса (`Index Cond: ... ROW(created_at, id) < ROW(...)`), а не фильтром.
- `id` в курсоре нужен по той же причине, что и в `ORDER BY`: у нескольких постов может быть одинаковый `created_at`.
- Новые посты не сдвигают следующие страницы (они выше курсора — появятся при обновлении первой страницы); удаление и отписка не вызывают пропусков.
- Курсор берётся только из строки, прочитанной из БД: `TIMESTAMPTZ` хранит микросекунды, а `Instant` из `Clock` может содержать наносекунды — «самодельный» курсор с наносекундами сломал бы сравнение.
- Страница с переходом «на номер N» больше не поддерживается — для бесконечной прокрутки она не нужна.

### 2.2. Частичный индекс по опубликованным постам

```sql
CREATE INDEX idx_posts_published_author_created
    ON posts (author_id, created_at DESC, id DESC)
    WHERE status = 'PUBLISHED';
```

- Удалённые посты в индекс не попадают: фильтр `status = 'PUBLISHED'` выполняется самим индексом.
- В индексе есть всё, что нужно для отбора (`author_id`, `created_at`, `id`), — `Index Only Scan` без чтения таблицы (`Heap Fetches: 0` при свежем `VACUUM`).
- Старый `idx_posts_author_created` полностью перекрывается новым (все запросы `posts` по автору и так читают только `PUBLISHED`) — предлагается удалить его в той же миграции, чтобы не платить за лишний индекс на каждой записи.
- Миграция — в файле индексов `008-create-posts-indexes.sql` (так сделано; план предлагал отдельный changeset `010` — см. «Отличия от плана»). На рабочей базе индекс создаётся `CREATE INDEX CONCURRENTLY` (в Liquibase — `runInTransaction:false`), чтобы не блокировать запись в `posts`; в учебном проекте достаточно обычного `CREATE INDEX`.

### 2.3. Не больше `limit` постов с каждого автора (`LATERAL`)

Глобальные первые `limit` постов ленты обязательно входят в объединение первых `limit` постов каждого автора. Поэтому достаточно для каждой подписки взять из индекса `limit` верхних постов (`LIMIT` внутри `LATERAL`), объединить и отсортировать. Объём работы — `подписки × limit` записей индекса, **независимо от числа постов и глубины страницы**.

### 2.4. Двухфазное чтение: сначала ключи, потом содержимое

Внутренний подзапрос отбирает только `id` и `created_at` (из индекса). Колонки страницы, включая `content`, читаются по первичному ключу только для итоговых `limit` строк.

### 2.5. Итоговый запрос

Первая страница — тот же запрос без условия курсора (в адаптере две SQL-константы, без склейки строк).

```sql
WITH page AS (
    SELECT lp.id, lp.created_at
    FROM subscriptions s
    CROSS JOIN LATERAL (
        SELECT p.id, p.created_at
        FROM posts p
        WHERE p.author_id = s.followed_id
          AND p.status = 'PUBLISHED'
          AND (p.created_at, p.id) < (?, ?)          -- только для следующих страниц
        ORDER BY p.created_at DESC, p.id DESC
        LIMIT ?                                     -- limit + 1
    ) lp
    WHERE s.follower_id = ?
    ORDER BY lp.created_at DESC, lp.id DESC
    LIMIT ?                                         -- limit + 1
)
SELECT p.id, p.author_id, p.title, p.content, p.status, p.created_at, p.updated_at
FROM page
JOIN posts p ON p.id = page.id
ORDER BY p.created_at DESC, p.id DESC;
```

`limit + 1` — чтобы без отдельного `COUNT` узнать, есть ли следующая страница: лишняя строка не возвращается, а её наличие означает «курсор следующей страницы = последний пост страницы».

### 2.6. Ограничение размера страницы

`limit` ограничивается сверху (предлагается `100`): стоимость запроса — `подписки × limit`, клиент не должен её раздувать. `limit <= 0` или `> 100` → `IllegalArgumentException` до обращения к БД (как сейчас для `limit <= 0`).

## 3. Что остаётся ограничением после этапа 1

- **Стоимость ~ `подписки × limit`.** 1 000 подписок — ~20 000 записей индекса на запрос (замер выше — 11–29 мс). У пользователя с 10 000+ подписок это уже сотни тысяч строк на каждый скролл.
- **Каждый запрос ленты — работа БД.** При очень большом числе читателей нагрузка на чтение растёт линейно; кеша нет.
- **Чтение чужой таблицы `subscriptions`** остаётся.

Насколько это критично, зависит от профиля нагрузки (п. 3.1).

### 3.1. Ожидаемый профиль нагрузки

Уточнение к `descr.md`:

- пользователей — несколько миллионов;
- читатель обычно подписан не больше чем на 200 авторов (типично 20–200);
- у отдельных авторов — очень много подписчиков, до нескольких миллионов.


**Число пользователей почти не влияет на время одного запроса.** Поиск в B-tree индексе логарифмический: при 2 млн и при 500 млн постов он отличается на один-два уровня дерева. Время запроса определяют подписки читателя и размер страницы — 200 × 21 ≈ 4 000 записей индекса. Миллионы пользователей увеличивают **число** запросов в секунду; это решается репликами для чтения и кешем первой страницы (п. 4.2), а не другим запросом.

Замер на данных `0091-sql-examples.sql` (PostgreSQL 17, 2 млн постов, прогретый кеш, страница 21 строка):

| Вариант | 202 подписки (Алиса) | 1 003 подписки (Дина) |
| --- | --- | --- |
| B. `JOIN subscriptions` + `ORDER BY` (исходный запрос, с частичным индексом) | 76 641 постов, 23 мс | 381 287 постов, 109 мс |
| A. `WHERE author_id = ANY(список авторов)` | — | 381 287 постов, 88 мс |
| **C. `subscriptions CROSS JOIN LATERAL`** (п. 2.5) | **4 242 записи индекса, 2,5 мс** | **21 063, 15 мс** |
| D. Список авторов (отдельный запрос, 0,05 мс) + `unnest(?::uuid[]) CROSS JOIN LATERAL` | 4 242, 2,1 мс | 21 063, 11 мс |

Выводы:

- **B и A не подходят даже при малом числе подписок.** Индекс упорядочен по дате внутри автора, а не по всей ленте, поэтому оба варианта читают **все** посты всех авторов из подписок и сортируют их. Время растёт с историей авторов: через пару лет у каждого не 400 постов, а тысячи. `IN (список)` и `JOIN` — два способа задать один и тот же набор авторов; ускоряет только ограничение «не больше `limit` с автора», которое даёт `LATERAL` с `LIMIT`.
- **C и D по нагрузке на БД равны,** у обоих время ограничено `подписки × limit` и со временем не растёт. Выбор между ними — архитектурный:

| | C (выбран) | D |
| --- | --- | --- |
| Обращений к БД на страницу | 1 | 2 (1 — если список подписок кешировать) |
| Чтение чужой таблицы `subscriptions` | да — согласованное исключение в `docs/architecture.md` | нет: список авторов — через API модуля `subscriptions` |
| Изменения кроме ленты | нет | метод в API `Subscriptions` («на кого подписан читатель»), `allowedDependencies = "subscriptions::api"` у `posts` |
| `posts` и `subscriptions` в разных базах / сервисах | придётся переписывать | работает как есть |

- **Популярные авторы (миллионы подписчиков) запросу C не мешают.** Стоимость страницы зависит от числа подписок **читателя**, а не от числа подписчиков автора. Миллионы читателей популярного автора берут из индекса одни и те же первые записи его диапазона — эти страницы индекса постоянно лежат в памяти (`shared_buffers`), поэтому такие чтения самые дешёвые. Публикация поста популярного автора — один `INSERT`, удаление — один `UPDATE`; пост сразу появляется и сразу исчезает во всех лентах. Это главный довод за сборку ленты при чтении (fan-out on read) при таком профиле.
- **Худший случай одной страницы:** 200 подписок × (`MAX_LIMIT` + 1) = 200 × 101 ≈ 20 000 записей индекса (как у Дины в замере — ~15 мс). Ограничивать число подписок для ленты не нужно.
- **Решение:** C — один запрос, без изменений API и зависимостей модулей. Переход на D — когда лента и подписки выделяются в отдельные сервисы или базы; он небольшой: меняется только источник авторов во `FROM` (`unnest(?::uuid[])` вместо `subscriptions`), часть с `LATERAL` остаётся той же.

## 4. Этап 2 — развитие (не реализуется в этой задаче)

### 4.1. Готовая лента на запись (fan-out on write) — при этом профиле не подходит

Идея: при публикации поста записывать его в таблицу `feed_items (follower_id, created_at, post_id, author_id)` каждого подписчика; чтение ленты — один диапазон индекса читателя, независимо от числа подписок. Наполнение — событиями модулей (`PostPublished`, `PostDeleted`, `Subscribed`, `Unsubscribed` в `api.event`, `@ApplicationModuleListener`, `spring-modulith-starter-jdbc`).

Почему не подходит:

- **Выигрыш — для читателя с тысячами подписок.** У нас их не больше 200: сборка при чтении стоит 2–15 мс (п. 3.1).
- **Проигрыш — на авторах с миллионами подписчиков.** Каждый их пост — миллионы вставок в `feed_items`, удаление — миллионы удалений; пост появляется в лентах с задержкой, растущей с числом подписчиков. Гибрид («звёзд» не размножать, подмешивать при чтении) возвращает нас к запросу C, только сложнее.
- Таблица `feed_items` — подписки × постов в «хвосте»: при миллионах пользователей это миллиарды строк.

Возвращаться к варианту стоит, только если профиль изменится: типичный читатель — тысячи подписок, а авторов с миллионами подписчиков нет.

### 4.2. Что действительно понадобится при миллионах пользователей

Нагрузку при профиле п. 3.1 создаёт число запросов, а не их стоимость. По мере роста, в таком порядке:

1. **Реплики PostgreSQL для чтения ленты:** запрос только читает, небольшое отставание реплики для ленты допустимо.
2. **Кеш последних постов автора** (Redis): ключ — автор, значение — его последние `MAX_LIMIT` пар `(created_at, id)` опубликованных постов. Инвалидация — событием публикации или удаления поста **этого автора**: один ключ, сколько бы подписчиков у автора ни было. Лента первой страницы собирается слиянием до 200 таких списков в приложении — та же логика, что `LATERAL` в п. 2.5, но без обращения к БД; содержимое постов — по `id` (тоже кешируется). Популярный автор — самый «горячий» ключ, и он лучше всего попадает в кеш.
   - **Кеш готовой первой страницы читателя** — только с коротким TTL (десятки секунд). Сбрасывать его событиями нельзя: пост популярного автора сбросил бы миллионы ключей — тот же fan-out on write, только в кеше.
3. **Кеш списка подписок** — если выбран вариант D: подписки меняются редко, тогда страница ленты — снова одно обращение к БД.
4. **Секционирование или шардирование `posts`** по `author_id`, когда таблица перестанет помещаться на один сервер: запрос `LATERAL` идёт по одному автору и ложится на шард автора; для этого нужен вариант D (подписки и посты на разных серверах). Шард популярного автора получает непропорционально много чтений — его снимают реплики шарда и кеш из пункта 2.

#### Подгрузка новых постов на первой странице (опрос раз в 0,5–2 минуты)

В задачу 41215-2 не входит; описано, чтобы будущий метод порта (например, `findFeedNewerThan(followerId, top, limit)` или `hasNewerPosts(followerId, top)`) не создал лишней нагрузки.

**Запрос** — тот же `LATERAL` из п. 2.5 с курсором в обратную сторону: `(p.created_at, p.id) > (?, ?)`, где курсор — верхний пост показанной страницы. Для каждого автора индекс спускается к его самому свежему посту; если тот старше курсора, автор пропускается — около 3 страниц индекса на подписку. Стоимость — `подписки × 3` страницы индекса, не зависит ни от числа постов, ни от числа подписчиков автора; обычно запрос возвращает ноль строк.

Замер на данных `0091-sql-examples.sql` (PostgreSQL 17, 2 млн постов):

| Запрос | 202 подписки (Алиса) | 1 003 подписки (Дина) |
| --- | --- | --- |
| Посты новее верхнего поста страницы (окно 2 минуты) | ~1 мс, ~600 страниц индекса | ~3 мс, ~3 000 |
| Только «есть ли новые?» (`EXISTS`) | ~0,5 мс, ~600 | — |
| Для сравнения: первая страница целиком | ~2,2 мс, ~3 650 | ~15 мс, ~18 000 |

**Дорого не одно обращение, а их число.** 1 млн пользователей онлайн, опрос раз в 30 секунд — ~33 000 запросов в секунду × ~1 мс: порядка 30 ядер БД только на ответы «новых нет». Поэтому:

1. **Опрос идёт в кеш, а не в БД.** Кеш времени последнего поста каждого автора (Redis, часть кеша из пункта 2): при публикации и удалении обновляется один ключ — автора, не подписчиков. Опрос сравнивает до 200 значений (`MGET`) с верхним постом страницы и обращается к БД, только если новое есть. Почти все опросы обходятся без БД.
2. **Опрос отвечает «есть ли новые» (или их число до порога), а не отдаёт посты.** Клиент показывает кнопку «Новые посты», по нажатию заново загружает первую страницу. «Склеивать» новые посты со старой страницей не нужно: если новых больше `limit`, между ними и старой страницей была бы дыра.
3. **Интервал 30–60 секунд со случайным разбросом** (чтобы опросы не шли волной), только для открытой вкладки; при уходе со страницы опрос прекращается.

**Подвох: пост, закоммиченный позже своего `created_at`.** Время проставляется в приложении до коммита. Пост с `created_at` 12:00:00.900 может стать видимым в 12:00:01.200; опрос в 12:00:01.000 его не увидит, а следующий ищет посты новее уже более свежего верхнего поста — и этот пост навсегда пропустит (в ленте он есть, но ниже). Решение — опрос с запасом: от «верхний пост − 10 секунд» (больше самой долгой транзакции публикации), уже показанные `id` клиент отбрасывает. Прокрутку вниз (`findFeedAfter`) это почти не затрагивает: поздно закоммиченный пост со временем ниже курсора прокрутки придёт на следующих страницах как обычно.

**Push вместо опроса** (WebSocket, SSE) при этом профиле не выигрывает: пост популярного автора — миллионы уведомлений подписчикам онлайн, тот же fan-out on write, только в сетевом слое. Допустим разве что как сигнал «есть новое» с объединением уведомлений, но это отдельная инфраструктура.

### 4.3. Рядом с лентой: подписчики популярного автора

Лента от числа подписчиков не зависит, но другие операции с таблицей `subscriptions` — зависят. Это модуль `subscriptions` и отдельные задачи, здесь — только чтобы не забыть:

- **Список подписчиков** (`/api/v1/subscribes/followers`) у автора с миллионами подписчиков нельзя отдавать целиком: нужны курсорные страницы и индекс `(followed_id, created_at DESC, id DESC)` или `(followed_id, follower_id)` (сейчас `idx_subscriptions_followed (followed_id)`).
- **Число подписчиков** — не `COUNT(*)` по миллионам строк при каждом показе профиля, а счётчик, который обновляется при подписке и отписке (или по событиям).
- **Таблица `subscriptions`** — миллионы пользователей × до 200 подписок: сотни миллионов строк. Ленте нужен только `uq_subscriptions_users (follower_id, followed_id)`; `idx_subscriptions_follower` его дублирует и стоит удалить (вопрос 2 раздела 6).
